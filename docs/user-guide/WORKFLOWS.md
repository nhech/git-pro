# Workflows and recovery

## Review, stage and commit

Changes is a native VS Code tree: each file has the icon of your file icon theme, its status is a coloured letter that follows your theme, and it works with the keyboard, multi-select and a count badge on the Git Pro icon. Use it to review the diff and stage or unstage files or folders. Hover or select a row for inline Open Changes, Open File, Discard and Stage or Unstage buttons (Stage All or Unstage All on group headers); right-click a row, a folder or a group for every contextual action, which applies to the whole selection when the row is part of it. The view title has Commit, Fetch, Pull, Push, Stage All and Unstage All, and **View as Tree** or **View as List** switches between grouping by folder and a flat list. While a merge, rebase, cherry-pick or revert is unfinished, its banner is the first row, with Resolve, Continue, Skip, Abort and Amend. Discard requires a reviewed confirmation because it removes working changes. Selection does not change the index.

The composer uses the current index and preserves partial staging performed in native Source Control. Under Conventional Commits in the menu, choose a type (the list is `gitPro.commit.conventionalTypes`), a scope and Breaking change: Git Pro writes `type(scope)!: ` at the start of the first line and leaves the rest of the message as it is, and the choices follow what you type. An empty list hides it. Hooks run by default. Amend and Skip Hooks require explicit review. A signing failure retains the draft; Git Pro does not disable signing or automatically retry a commit. If Commit & Push commits successfully but push fails, the result reports these outcomes separately. Inspect the successful commit before retrying the push.

## File review

**Single lines** are staged with VS Code's own commands, which work in the diff Git Pro opens for a changed file (Index ↔ Working Tree): select the lines in the right-hand editor, right-click, and choose **Stage Selected Ranges** or **Revert Selected Ranges**. To unstage single lines of a file that is already staged, use the built-in Source Control view, whose diff offers **Unstage Selected Ranges**.

**Hunk Actions** checks a reviewed text patch before applying only that hunk. Unsaved files or stale reviews block the action. Binary, new/deleted, rename and mode-change cases use native SCM guidance. **Commit File** commits the full saved version of one file with Git's `commit --only`, preserving unrelated staged files.

Enable active-line blame to see author, UTC author date, hash and summary. Dirty buffers suppress on-disk attribution; uncommitted lines have no commit link. Optional CodeLens opens File History for saved regular files in open trusted repositories.

## Sync and branches

Fetch reads remote updates. Pull requires a clean tree and defaults to fast-forward only; choose merge or rebase explicitly in [settings](SETTINGS.md). Ordinary push confirmations are optional. Force Push with Lease always requires a fresh exact-lease preview and confirmation; there is no setting to disable this review.

The **Branches** view lists local and remote branches of the selected repository (the first 200 of each group; search for the rest). A local branch that is ahead of or behind its upstream shows `↑2 ↓1` next to its name; the counts come from the last fetch, and a slow repository shows the list without them. A click only selects a branch. Right-click it for checkout (a remote branch becomes a tracking branch), rename, set or unset the upstream, copy the name, delete, and the compare, merge and rebase actions; the inline button beside a branch opens the same choices as a list. With a branch selected, **F2** renames a local branch, **Delete** deletes one (after the usual confirmation; ⌘Backspace on macOS) and **Ctrl+C** (⌘C) copies its name. The **Remote** group lists the remote branches Git already has, with **Fetch** and **Refresh** in the view title; a repository with no remote says so instead of offering a fetch.

## History and comparison

History stays pinned to its repository. Choose branch/tag scope and filters; select a commit to inspect Details, parent choice and changed files. Right-click a commit for Checkout (Detached), Create Branch, Create Tag, Cherry Pick, Revert, Interactive Rebase from Here, Compare with Current, Compare with Working Tree, Open on Remote, Copy Remote URL and Copy Commit Hash or Message; each choice shows the same preview and confirmation as the matching action elsewhere. Open on Remote and the `#123` links in a commit's subject and message open its page on GitHub, GitLab, Bitbucket or Codeberg in your browser. The link is built from the address of the remote the current branch follows (else `origin`) and is never fetched; a company server is named in `gitPro.remoteHosts`. Compare exact revisions through History's Compare form, or branches in the Compare tab (below). File History follows renames across parents with explicit continuation when traversal reaches its bound.

History loads 25–100 commits per page and stops at 2,000 loaded commits. Load more explains whether the history ended or the load cap was reached. Refresh starts a new snapshot. Details mounts 200 files per page; comparison sides use 25 entries per page. Containing refs load after the rest of Details; in very large repositories they can take a while or be reported as unavailable without affecting the details. A commit whose file list or message exceeds the read bound shows its metadata with a note to use native Git. Text revisions require UTF-8 and at most 5 MiB; unsupported binary/submodule/symlink cases show guidance.

## Compare branches

In the Branches view or Branch Actions, choose **Compare with Current** or **Show Diff with Working Tree** on any branch except the checked-out one. **Compare with Another Branch…** works on every branch, including the checked-out one and remote branches: pick the other branch or tag from a list, or choose **Enter a revision…** at the end of the list to type a commit ID or an expression such as `HEAD~3`. The checked-out branch is always shown on the right. Ctrl/Cmd-click exactly two branches for **Compare Branches**. The **Remote** group of the Branches view lists the remote branches Git already has; use **Fetch** in the view title (or turn on auto-fetch in settings) to download new ones. Tags → Compare With HEAD opens the same tab. Both refs are pinned to commits when the tab opens; if a branch moves later, the tab says so and **Refresh** pins it again.

The Compare tab lists "Commits in X, not in Y" for each direction, 25 at a time, with **Swap**. Files show **Since fork** (what the branch changed since the merge base; the default) or **Tip to tip**. With several merge bases the first one is used; unrelated histories fall back to tip to tip. A commit that has the same change on the other side under another ID (a cherry-pick or a rebased copy) is marked `≈`, and the footer counts those commits; the check is skipped when the two sides together have more than 2,000 commits. Select a commit to see only its files, and **All changes** to return. Rows of a commit have **Copy Revision Number** and **Show in History** buttons on hover and focus. **Open All Changes** opens up to 300 text files in one multi-diff editor; binary files are left out. Files are a nested tree, with folders first, a chain of folders that hold nothing else on one row (`src/main/java`) and a count on every folder (or a list, with the button above them). Press **V** on a file, use its button or right-click it to mark it as **viewed**, as in a code review: a viewed file is dimmed with a check and counted in the footer, and in a working-tree comparison the menu marks the whole selection. The marks are kept in the workspace for that exact comparison (the same two commits and folder), also after the tab is closed, for the 30 most recent comparisons; the files of a single commit have no marks. Click a file to open its diff **beside** the Compare tab, so the list stays in view and the next click replaces the diff; turn this off with `gitPro.compare.openDiffsBeside`. **Alt+Down** and **Alt+Up**, or the arrow buttons above the list, open the next or previous file's diff in the order the list shows. Right-click a file for Open Diff, **Compare with Local**, Open File and Copy Path. Above the files, type part of a name and choose Added, Modified, Deleted or Renamed to narrow the list; the count, paging and Open All Changes follow what is shown. Right-click a commit in either list for the same commit choices as in History, plus Show Changed Files.

**Show Diff with Working Tree** compares a branch with your tracked working files, staged or not; untracked files are not compared. The working file is the editable side. **Get from Branch** (up to 100 selected files) replaces those working files with the branch version and deletes the ones the branch does not have, after a confirmation that lists both. It never changes the index, and it refuses files with unsaved edits and untracked or ignored files of the same name, which Git could not give back.

**Compare with Branch or Tag…** in the Explorer and editor tab menus compares one file with a branch or tag; the working file stays editable. On a folder it opens the branch or tag against the working tree, limited to the files inside that folder; on the repository root it compares everything.

## Resolve conflicts

When a Git Pro merge, pull, rebase, cherry-pick, revert or stash stops on conflicts, the **Conflicts** tab opens (setting `gitPro.conflicts.autoOpen`). Open it any time with **Resolve Conflicts…** from the Changes view, its banner or the status bar menu. Each row shows the file, its kind and the state of the Yours and Theirs sides, named after their branches. During a rebase, Yours is the commit being replayed (Git `--theirs`) and Theirs is the upstream; each confirmation names the Git side.

- **Accept Yours** / **Accept Theirs** (Alt+Y / Alt+T) resolve up to 100 selected files and stage them in one step after one confirmation. If the chosen side has no file, the file is deleted. Files with unsaved edits or open in a merge editor are refused.
- **Merge…** (Alt+M, Enter or double-click) opens VS Code's merge editor as Yours | Result | Theirs; the Result is the real file. **Apply & Next** in the editor title saves the Result, stages it and opens the next file. VS Code's own Complete Merge saves without staging, so Git Pro then offers Mark Resolved. VS Code's "Accept All … from Left/Right" tooltips keep their own Incoming/Current wording. VS Code's default merge editor layout puts Yours and Theirs side by side above the Result; **More Actions → Use Column Layout in Merge Editor** switches the next one to three columns, and VS Code keeps that layout.
- Right-click a conflicted file for Merge…, Accept Yours, Accept Theirs, **Mark Resolved**, Open File and the three compares; the choices apply to the whole selection when the file is part of it, and the menu shows the Alt+Y, Alt+T and Alt+M shortcuts. **Mark Resolved** stages a text file changed on both sides with no conflict markers left. Binary files and modify/delete or add/rename conflicts are resolved with Accept only, so a side is never chosen silently. Symlinks, submodules and files larger than 5 MiB need native Git.
- A cherry-pick, revert, merge or stash apply run while a rebase is stopped (for example at an `edit` step) owns its conflicts: Yours is then your current work (Git `--ours`), and Continue or Abort act on that command first.

The Changes view shows a banner such as "Merging feature into main · 3 conflicts" with Resolve, Continue and Abort, and the status bar shows the conflict count; clicking it opens the same actions. Continue stays disabled until every conflict is staged and always asks first; Continue Merge can edit the merge message. After a Git Pro stash pop stops on conflicts, the stash is kept, and the tab offers **Drop Stash…** once everything is resolved.

## Advanced operations and tools

Advanced actions review fresh merge/rebase/cherry-pick/revert/reset previews. Branch Actions also offers **Merge into Current…** and **Rebase Current onto This…** with the same review. Continue, Skip and Abort depend on actual Git operation state. Resolve conflicts, save the intended content and review staging before continuing. If no merge editor can open, Git Pro opens the file with its conflict markers.

Canceling an operation may leave Git state changed. Refresh and inspect the repository before retrying. Git Pro coordinates its own mutations in one extension host; other tools can still change the repository concurrently.

No automatic destructive retry is performed.

## Interactive rebase

Run **Interactive Rebase Planner** from the Command Palette (or Advanced Actions → Interactive Rebase) and enter the ancestor to rewrite after; the default is `HEAD~1`. The planner lists the commits after it, oldest first, for a linear range of 1–200 commits. A range that contains merges needs native Git.

Choose Pick, Reword, Edit, Squash, Fixup or Drop for each commit, from the Action list or by right-clicking the commit, and reorder with Move Up and Move Down (Alt+Up and Alt+Down) or by dragging. Reword opens a message editor, and the message is used as you type it, including lines that start with `#`. **Review plan** shows the whole plan, and nothing is rewritten until you confirm it. **Use native planner** offers the same plan as a quick pick.

If the rebase stops on a conflict or at an Edit step, the Changes banner, the status bar and the Conflicts tab follow it, and Continue, Skip and Abort act on the real Git state. A plan that rewords commits runs with a comment character of its own so that those `#` lines survive; Git Pro's Continue uses it automatically, and when the plan stops Git Pro shows the exact `git -c 'core.commentChar=…' rebase --continue` command for a terminal. Rewriting commits you already pushed needs Force Push with Lease afterwards, which is reviewed like any other force push.

## Stashes, tags, remotes and worktrees

Repository Tools groups four lists. A click only selects an item; right-click a group or an entry for its choices (the inline button opens them as a list). **Delete** on a selected stash, tag, remote or worktree starts its removal, which asks first, and **F2** renames a remote. **Stashes**: create one (tracked files only, or tracked and untracked), inspect its files, apply, pop, create a branch from it or drop it; a pop that stops on conflicts keeps the stash. **Tags**: create, view the message, compare with HEAD, check out detached, create a branch, push, delete locally or on the remote; tag pushes and deletions are explicit. **Remotes**: add, fetch, push a local branch, set a branch upstream, rename, set the fetch or push URL, prune and remove. **Worktrees**: add, open in a new window, remove and prune stale metadata; creating or removing an external worktree needs approval of the exact path.
