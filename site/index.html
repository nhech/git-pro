Git Pro: Git workflows for VS Code, from one sidebar.

Review and stage changes, write commits, explore History and recover rebases, merges and stashes.

Built on VS Code's built-in Git extension. Destructive actions require a reviewed confirmation.

Features

From reviewing a diff to recovering a rebase

Six areas of everyday Git work in one Activity Bar container. Native rows, status letters, codicons and your color theme, with one accent color you can change.

Changes & commits

File and folder staging, native diffs, reviewed discard, commit, amend and signoff.

  • Staged, working tree, untracked and conflict groups with right-aligned status letters
  • Inline Open Changes, Open File, Discard and Stage on hover; right-click for every action
  • Commit box with Ctrl+Enter (⌘Enter on macOS), plus Commit & Push, Amend, Sign-off, Skip hooks and message history
  • Commits the current index, including partial staging from native Source Control

Branches & sync

Branch and upstream actions, fetch, explicit pull strategy, push, init and clone.

  • Pull defaults to fast-forward only; merge or rebase is an explicit choice
  • Force Push with Explicit Lease always shows a fresh exact-lease preview and confirmation
  • Optional auto-fetch with per-repository schedules and backoff after failures

History & compare

Commit graph, filters, details, merge-parent selection, comparison and rename-aware File History.

  • Column-based History; the accent marks HEAD and the current branch
  • Details with parent choice, changed files and containing refs
  • Compare revisions without leaving VS Code
  • File History follows renames across parents

File review

Text hunk actions, saved-file commits and optional active-line blame and CodeLens.

  • Hunk Actions check a reviewed text patch before applying only that hunk
  • Commit File commits the full saved version of one file and preserves unrelated staged files
  • Active-line blame and a read-only File History CodeLens, both off by default

Advanced operations

Merge, rebase, cherry-pick, revert, reset and operation recovery; interactive linear rebase.

  • Review fresh previews before a merge, rebase, cherry-pick, revert or reset is applied
  • Continue, Skip and Abort follow the actual Git operation state
  • Interactive Rebase Planner for linear ranges of 1–200 commits
  • Conflicts use VS Code's native Merge Editor, with guidance when it is unavailable

Repository tools

Stashes, tags, remotes and worktrees, with a repository selector for multi-repository workspaces.

  • Tag pushes, tag deletions and worktree destinations are explicit
  • Creating or removing an external worktree needs approval of the exact path
  • A stash pop conflict keeps the stash

Careful by default

  • Opt-in extras

    Auto-fetch, active-line blame and CodeLens stay off until you enable them.

  • Review before rewrite

    Discard, Amend, Skip Hooks, force push and advanced operations are reviewed first. No setting disables destructive confirmations.

  • Your Git setup

    Uses your Git identity, credential helpers, SSH agent and signing. A signing failure keeps your draft.

  • No telemetry code

    The extension contains no telemetry or analytics code, and operation logs always redact credentials.

How it works

Three steps to your first commit

Git Pro works on top of VS Code's built-in Git and the repository you already have open.

  1. 1

    Install Git Pro

    Install it from the Extensions view once the Marketplace listing is live, or run Extensions: Install from VSIX... for a downloaded package. Reload VS Code if requested.

  2. 2

    Open a trusted repository

    Open your repository folder, review workspace trust, then select Git Pro in the Activity Bar. Choose the repository if more than one is available.

  3. 3

    Review, stage and commit

    Open a diff, stage the files you intend to commit, type a message in the Commit box and press Ctrl+Enter (⌘Enter on macOS).

Requirements

  • VS Code 1.100.0 or newer
  • Git available on the extension host
  • VS Code's built-in Git extension, enabled
  • A trusted filesystem workspace

Browser and virtual workspaces, such as vscode.dev and github.dev, are unsupported.

First steps

  1. Open your repository folder and review workspace trust.
  2. Select Git Pro in the Activity Bar and choose the repository if more than one is available.
  3. Open Changes, review a diff and stage the intended files. Selecting rows does not stage them.
  4. Type a message in the Commit box and press Ctrl+Enter (⌘Enter on macOS) or Commit, or use the menu beside Commit for Commit & Push, Amend, Sign-off, Skip hooks and message history.
  5. Run Git Pro commands from the Command Palette for History, File History, branches, advanced actions and repository tools.

Git Pro assigns no global shortcuts; add your own in Keyboard Shortcuts. For diagnostics, run Git Pro: Show Output and review the log before sharing it.

Settings worth knowing

Open Settings and search for gitPro. Resource settings apply to the selected repository.

SettingDefaultWhat it does
gitPro.pull.strategy"ff-only"Pull strategy: ff-only, merge or rebase. Divergence requires an explicit merge or rebase choice.
gitPro.confirmBeforePushfalseConfirm pushes to the configured upstream.
gitPro.commit.subjectLimit72Subject warning length (20–200). It warns; it never truncates.
gitPro.commit.messageHistoryLimit20Messages kept per repository in workspace state (0–100; 0 hides history).
gitPro.autoFetch.enabledfalsePeriodically fetch remotes, every 5 minutes by default, with backoff after failures.
gitPro.blame.enabledfalseShow author and commit for the active line.
gitPro.codeLens.enabledfalseRead-only File History CodeLens on saved files. No automatic Git read.
gitPro.changes.groupBy"status"Show paths flat (status) or as folders (folder) within each group.

The Settings guide lists all 17 settings with ranges and scopes. To change the accent color, set the theme color gitPro.accent:

"workbench.colorCustomizations": {
  "gitPro.accent": "#3794ff"
}

FAQ

Questions, answered from the docs

How is Git Pro licensed?

Under the MIT license, copyright 2026 longtd. The license text and third-party notices are in the GitHub repository.

What do I need to run it?

VS Code 1.100.0 or newer with the built-in Git extension enabled, Git available on the extension host, and a trusted filesystem workspace.

Does Git Pro replace VS Code's built-in Git?

No. Git Pro requires the built-in Git extension and builds on it. Line-level partial staging stays in native Source Control, and Git Pro commits that index. Conflicts use VS Code's native Merge Editor; when it is unavailable, use the conflict guidance and native diffs. Authentication and signing use your configured Git identity, credential helpers, SSH agent and signing settings.

What does "preview" mean?

Git Pro {{VERSION}} is a preview: behavior and limits may change between versions. Known limits, such as the 2,000 loaded commits in History and interactive rebase for linear ranges of 1–200 commits, are listed in Compatibility and limitations.

Which features are off by default?

Auto-fetch, active-line blame and the File History CodeLens are opt-in. Turn them on in Settings with gitPro.autoFetch.enabled, gitPro.blame.enabled and gitPro.codeLens.enabled. The CodeLens does not read history until you open File History. Git Pro also assigns no global keyboard shortcuts.

How does it handle destructive operations?

Discard requires a reviewed confirmation. Force Push with Explicit Lease always shows a fresh exact-lease preview, and advanced merge, rebase, cherry-pick, revert and reset actions show a fresh preview before applying. No setting disables these confirmations, and Git Pro performs no automatic destructive retry.

Canceling a Git operation can still leave the repository changed and does not imply a rollback, so refresh and inspect the repository before retrying.

Does it work in the browser, over Remote or in containers?

Browser and virtual workspaces, such as vscode.dev and github.dev, are unsupported, and so are untrusted workspaces. Git Pro runs where the workspace is, so remote workspaces need Git and credentials on the remote host. Remote WSL and Dev Containers have not completed release validation.

Where do I report a problem?

Open an issue on GitHub Issues. Run Git Pro: Show Output for diagnostics; credentials are redacted from operation logs, but review any log before sharing it.
